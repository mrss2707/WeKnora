Đánh giá chuyên sâu Hệ thống Memory V2 × WeKnora

  Tổng quan

  Memory V2 là module ~13,000 dòng code (server-side) + ~3,200 dòng CLI + ~400 dòng SDK client + ~5,100 dòng
  frontend, triển khai full-stack memory system trên PostgreSQL + pgvector. Thiết kế theo kiến trúc
  RAG-native memory — không phải memory cho agent loop (có system riêng), mà là persistent knowledge store
  cho toàn bộ tenant.

  ---
  1. Kiến trúc — Điểm mạnh

  1.1 Layering rõ ràng, dependency inversion tốt

  Handler → Service (interface) → Repository (interface) → PostgreSQL
                                        ↑
                                 CacheInvalidator

  - Interface segregation chuẩn: MemoryServiceV2 (9 methods), MemoryRepositoryV2 (12 methods),
  CacheInvalidator (3 methods) — mỗi interface đúng một responsibility
  - DI qua uber-go/dig: container.go wire tất cả dependency, chọn V1 vs V2 runtime qua config flag
  MemoryV2.Enabled
  - Plugin pattern cho chat pipeline: MemoryPluginV2 đăng ký 2 events (MEMORY_RETRIEVAL, MEMORY_STORAGE),
  tách biệt hoàn toàn với phần còn lại

  1.2 Dual-write pipeline design (CLI hooks + MCP tools)

  Hai đường dẫn độc lập để agent tương tác với memory:

  ┌───────────┬─────────────────────────────────────────────┬──────────────────────────────────┐
  │ Đường dẫn │                   Cơ chế                    │             Trigger              │
  ├───────────┼─────────────────────────────────────────────┼──────────────────────────────────┤
  │ Hooks     │ weknora memory hook session-start/post-tool │ Agent platform gọi tự động       │
  ├───────────┼─────────────────────────────────────────────┼──────────────────────────────────┤
  │ MCP Tools │ memory_recall/save/graph/status             │ Agent gọi chủ động qua tool call │
  └───────────┴─────────────────────────────────────────────┴──────────────────────────────────┘

  → Redundancy có chủ đích: hooks là passive (auto-triggered), MCP tools là active (agent-initiated). Không
  conflict.

  1.3 Ingestion pipeline 10 bước có cấu trúc tốt

  validate → fingerprint dedup → embed → semantic dedup → type detect → tags → importance → tier → store →
  lint → entity extract

  Mỗi bước có error handling riêng, có typed errors (ErrMemoryValidation, ErrMemoryDuplicate), merge logic rõ
   ràng.

  1.4 Hybrid search 8 bước với weighted fusion

  BM25(0.15) + Cosine(0.45) + HubScore(0.25) + Importance(0.15)
  → recency boost → verdict filter → session boost → score threshold → sort → limit

  Công thức fusion có cơ sở lý thuyết tốt. Fallback rõ ràng khi thiếu embedder hoặc ParadeDB.

  2. Điểm yếu & Rủi ro

  2.1 CRITICAL: Tenant isolation trong MemoryFilter không nhất quán

  Code ở search.go:56 khi gọi CosineSearch:
  cosineFilter := &types.MemoryFilter{
      TenantID: filter.TenantID,
      Verdicts: filter.Verdicts,
  }
  → Bỏ sót UserID, SessionID, MemoryType, Tier — cosine search trả về tất cả memory của tenant, không filter
  theo user/session. Sau đó merge với BM25 results (đã filter). Điều này gây ra:
  - Cosine results có thể bao gồm memory của user khác → applySessionBoost sẽ boost sai
  - Merge score bị skew vì cosine pool rộng hơn BM25 pool

  Khuyến nghị: Pass đầy đủ filter vào CosineSearch, hoặc ít nhất UserID + SessionID.

  2.2 CRITICAL: AddEpisode bỏ qua TenantID

  service.go:351:
  memory := &types.AgentMemory{
      TenantID:   "",  // ← EMPTY!
      Content:    content,
      ...
  }
  → Memory được tạo với TenantID = "", không thuộc về tenant nào. Điều này:
  - Vi phạm multi-tenant isolation
  - Memory sẽ không bao giờ được tìm thấy trong search (search filter by tenant_id)
  - Lãng phí storage

  Root cause: AddEpisode nhận userID, sessionID nhưng không nhận tenantID. Caller ở
  chat_pipeline/memory_v2.go:106 cũng không pass tenantID.

  Khuyến nghị: Thêm tenantID vào signature của AddEpisode và pass từ chatManage.TenantID.

  2.3 HIGH: buildSearchQuery không dùng index hiệu quả

  Query construction ở repository.go:212-241:
  db.Where("tenant_id = ?", filter.TenantID).
     Where("deleted_at IS NULL")
  → Dùng tenant_id index nhưng không dùng kb_id index. Khi filter có kb_id, index
  idx_agent_memories_tenant_kb bị bỏ qua.

  Ngoài ra, nếu filter.Verdicts được set rỗng (len=0 nhưng không nil), code sẽ đi vào nhánh IN () — SQL
  syntax error.

  2.4 HIGH: TokenBudgetManager không bao giờ dùng chat model thực

  service.go:185:
  tokenBudget: NewTokenBudgetManager().WithChat(nil),
  Và getChat() line 264-266 có update chat model. Nhưng TokenBudgetManager thực sự chỉ dùng estimateTokens()
  (length/4), không gọi LLM summary. Điều này OK về mặt logic, nhưng tên hàm summarize() trong
  token_budget.go misleading — gợi ý LLM involvement nhưng thực tế không hoạt động.

  2.5 MEDIUM: Worker StartWorkers có race condition

  s.wg.Add(7)
  go runWorker(ctx, &s.wg, s.entityExtractor.Run)
  ...
  if s.config.CacheWarmer.Enabled {
      s.wg.Add(1)  // ← Add trong goroutine khác với Add(7) ở trên
      go runWorker(ctx, &s.wg, s.cacheWarmer.Run)
  }
  sync.WaitGroup.Add() phải được gọi trước khi goroutine bắt đầu chạy. Ở đây Add(7) được gọi, goroutines bắt
  đầu, rồi Add(1) được gọi sau → race condition nếu cache warmer goroutine gọi wg.Done() trước khi wg.Add(1)
  kịp thực thi.

  Khuyến nghị: Đếm tổng số workers trước khi start, hoặc dùng counter riêng.

  2.6 MEDIUM: Dreamer worker lấy memory không phân biệt tenant

  dreamer.go:101-104:
  filter := &types.MemoryFilter{
      TenantID: tenantID, // "" khi gọi từ dreamPass()
      Limit:    50,
  }
  candidates, _, err := d.repo.Search(ctx, filter)
  Khi tenantID = "", buildSearchQuery sẽ WHERE tenant_id = '' → trả về 0 results. Dreamer sẽ không bao giờ xử
   lý được memory khi chạy từ background loop. Chỉ hoạt động khi gọi qua HTTP API với tenantID cụ thể.

  2.7 MEDIUM: Cache interface duplication

  Có 3 cache implementations cho memory:
  1. cli/internal/memory/cache.go:MemCache — CLI-side hook dedup
  2. service/memory_v2/service.go:MemoryCache — Server-side embedding cache
  3. repository nhận CacheInvalidator interface

  → Không có shared cache layer. Code tương tự nhau nhưng riêng biệt.

  2.8 MEDIUM: Stop words trong ingestion quá thô

  isStopWord() định nghĩa inline ~120 stop words. Các từ như "was", "were" cũng trong stopword list, nhưng
  lại vừa là stopword vừa là keyword trigger trong detectMemoryType():
  episodicKeywords := []string{"happened", "occurred", "was", "were", ...}
  "was" và "were" bị suggestTags loại bỏ (stopword) nhưng detectMemoryType dùng làm signal → inconsistency
  logic.

  2.9 LOW: saveMemory set CreatedAt 2 lần

  ingestion.go:98: memory.CreatedAt = now nhưng repository.go:44 cũng set memory.CreatedAt = now. GORM sẽ
  dùng giá trị cuối cùng, nhưng double-set là không cần thiết.

  3. Đánh giá tích hợp

  3.1 Chat Pipeline → Memory (hoạt động ✓)

  Flow MEMORY_RETRIEVAL → MEMORY_STORAGE hoạt động đúng. Memory context được append vào UserContent. Storage
  chạy async (go routine) → không block chat response.

  Vấn đề: context format ở memory_v2.go:71-74 dùng plain text format đơn giản:
  memoryStr += fmt.Sprintf("- %s (Summary: %s)\n", ep.CreatedAt.Format("2006-01-02"), ep.Summary)
  Trong khi RetrieveMemory ở service trả về XML format (qua packContext). Format không consistent với search
  API.

  3.2 Agent Loop → Memory (KHÔNG tích hợp ✗)

  agent/engine.go có memoryConsolidator nhưng đây là system riêng cho context-window compression (tóm tắt
  conversation cũ khi vượt token budget). Agent engine không gọi MemoryServiceV2.RetrieveMemory() hay
  memory_recall MCP tool.

  Memory V2 chỉ được trigger qua:
  1. Chat pipeline plugin (khi chat thông thường)
  2. MCP tools (khi agent chủ động gọi)

  → Agent ReAct loop không tự động inject memory context. Agent phải chủ động dùng memory_recall tool.

  3.3 REST API → Frontend (hoạt động ✓)

  11 endpoints, pagination, filter, RBAC đầy đủ. Frontend có Pinia store + 7 Vue components. Full CRUD +
  search + graph visualization + health dashboard.

  3.4 MCP → Agent (hoạt động ✓, 4 tools)

  4 MCP tools (memory_recall, memory_save, memory_graph, memory_status) được expose qua weknora mcp serve.
  Validation input đầy đủ, error handling chuẩn CLI typed errors.

  4. Worker WaitGroup.Add race condition

  6. filter.Verdicts empty-but-not-nil → SQL syntax error

  8. Cache distributed (Redis) cho multi-instance
  9. Agent engine tự động inject memory context
  10. Audit log cho memory mutations

  8. Đánh giá tổng thể

  Điểm mạnh cốt lõi: Memory V2 là một hệ thống được thiết kế có chủ đích với kiến trúc rõ ràng, ingestion
  pipeline 10 bước, hybrid search 8 bước, và 7 background workers. Code có test coverage tốt, error handling
  typed, và multi-platform setup engine linh hoạt.

  Điểm yếu cốt lõi: Tích hợp với agent loop còn lỏng lẻo — agent phải chủ động gọi tool thay vì tự động
  inject. Bug TenantID = "" trong AddEpisode là lỗi nghiêm trọng về multi-tenancy. Search pipeline có
  inconsistency giữa BM25 và cosine branch.

  Overall: 7.0/10 — Hệ thống hoạt động được, thiết kế tốt về mặt kiến trúc, nhưng có các vấn đề
  production-readiness cần giải quyết trước khi triển khai rộng.
